## Problem & user

RocketShip PMs need this handled: Juno is the PM's triage and synthesis partner. It turns noisy, conflicting inputs (tickets, exec asks, sales notes, Slack) into prioritized, evidence-backed recommendations, using RocketShip's own strategy framework as the judge.Core task: Each week, take the raw signals and:  Classify each against the P0–P3 framework, with reasoning cited to the one-pager's definitions. Check feasibility against the engineering capacity note and the roadmap. Surface conflicts, commitments nobody made, and unknowns. Draft the PM's next actions: stakeholder messages, roadmap changes, questions to ask.. Juno does this inside limits a human set on purpose, and defends every call it makes.

## 01 Context · Data Requirements

**Required sources, and exclusions**

Layer	Contents	Freshness
Stable	Strategy one-pager: pillars, P0–P3 definitions with explicit exclusions, metrics	Changes rarely
Slow	Roadmap (committed vs. not, owners, targets)	Weekly
Fast	Capacity note, pipeline snapshot, raw signals	Weekly or live

Juno should also carry a small glossary and people map (who owns which pod, who is out, e.g. Marcus on leave) and each source's author and reliability. A rep's call notes, a VP's capacity note, and a CEO's email carry different weight on different questions.

**How fresh must it be**

CTX-01
MUST
Load the strategy one-pager (pillars, P0–P3 definitions, explicit-exclusion lists, metrics) at the start of every run.
Run log records the one-pager version. If it is missing, classification is skipped and the brief says so.
CTX-02
MUST
Load the roadmap each run with committed vs. not-committed status, owner and target date per item.
Every roadmap item in context has all three fields; items missing a field are listed as data gaps.
CTX-03
MUST
Load the fast tier (capacity note, pipeline snapshot, raw signals) each run with a retrieved-at timestamp.
Any fast-tier source older than 7 days (placeholder) is flagged stale in the brief.

## 02 Tools · System Capabilities

**The verb list**

Read: the CRM, roadmap, ticketing, Slack channels, and capacity notes.
Analyze: a signal-classifier routine (framework lookup plus capacity check) and duplicate and root-cause clustering.
Draft: briefs, Slack and email drafts, roadmap-change proposals, and PRD stubs.
No write tools to the roadmap, CRM, or outbound channels. Output goes to the PM.

**Deliberate omissions**

TL-01
MUST
Provide read connectors for CRM, roadmap, ticketing, capacity notes and an allowlist of Slack channels, each using read-only credentials.
A write call through any connector is rejected at the API or credential layer, not by the model.
TL-02
MUST
Provide a signal-classifier tool that takes a cluster and returns: priority (P0–P3), quoted definition, exclusion-list check result, capacity check result, and confidence.
Output validates against a fixed schema; a result without a quoted definition fails validation.
TL-03
MUST
Provide a clustering tool for duplicates and shared root cause that returns cluster ID, member signal IDs, root-cause hypothesis and confidence.
Every input signal lands in exactly one cluster; singleton clusters are allowed.

## 03 Loop · AI Costs & Latency

**Turn ceiling and escalation**

Ingest new signals and diff them against last week's state.
Cluster them by root cause (Sarah, Dave, Initech and Pearson's export rumor collapse into one issue).
Classify each cluster against P0–P3, quoting the definition that applies.
Check feasibility against pod capacity and roadmap commitments.
Detect conflicts: unscoped promises, deadlines at risk, work with no pillar, and sources that disagree.
Rank and recommend with options and trade-offs, not a single verdict.
Draft follow-ups, then wait for PM approval.
Log the decisions the PM makes.

**Latency and cost target**

LP-01
MUST
Run weekly on a schedule and on demand by the PM.
A scheduled run and a manual run on the same inputs produce the same brief structure.
LP-02
MUST
Ingest new signals and diff against last week's state, labeling each as new, changed, resolved or unchanged.
The brief opens with the diff counts; resolved items cite the evidence of resolution.
LP-03
MUST
Cluster signals by duplicate and root cause (TL-03) before classifying.
On the eval set, Sarah, Dave, Initech and the Pearson export rumor form one cluster.
LP-04
MUST
Classify each cluster against P0–P3, quoting the definition that applies.
Every cluster in the brief shows its priority and a verbatim definition quote.

## 04 Memory · Data Requirements

**What persists, at what scope**

Decision log: what the PM decided, why, and when. Juno never re-litigates a closed call without new evidence.
Open commitments ledger: promises made externally (Slack alerts, TikTok, the AI-dashboard press line) with owner and walk-back status.
Account and issue threads: Pearson, Acme, Initech and Globex, with last-touched dates, so Globex doesn't quietly drop off.
PM preferences: format, depth, and tone for stakeholder drafts.
Memory should hold conclusions and links to sources, not copies of raw customer text. Entries should expire or be re-verified, since capacity and deal status go stale quickly.

**Expiry and write rules**

MEM-01
MUST
Keep a decision log with: decision, rationale, date, decider, evidence links, and reopen condition.
Every entry has all six fields.
MEM-02
MUST
Never re-litigate a logged decision unless it cites new evidence not in the original entry.
A brief that reopens a decision names the new signal ID; a test reopening with old evidence only fails.
MEM-03
MUST
Keep an open-commitments ledger: commitment, who made it, to whom, channel, date, owner, and status (open, walking back, walked back, honored). Seed with Slack alerts, TikTok and the AI-dashboard press line.
All three seed commitments exist with an owner; every open commitment appears in each weekly brief until closed.
